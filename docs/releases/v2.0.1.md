# v2.0.1 — Registro origin, location invariants, and worktree isolation

Patch release that corrects validation, status filtering, location invariants, Registro metrics, and Docker worktree isolation. No breaking API; all changes are corrective and backward compatible with `v2.0.0` data and images.

## What changed

### Service validation and status filter

Inline field validation replaces the generic `Datos inválidos` alert. `POST`/`PUT` at `app/api/services/route.ts` return `fieldErrors` per field from the canonical `lib/schemas.ts`; `components/services/ServicesModal.tsx` removes its divergent local schema, renders red borders and per-field messages via a type-safe resolver, and requires `sku`, `failureDescription`, and `entryDate`. `components/services/ServicesDashboard.tsx` status dropdown drops the `badgeClass` pill; the selected item shows only a right-side check, matching `Todos los estados` and preserving exclusive single-status behavior. RUT regression `41.421.442-1 → 8` added at `tests/unit/rut.test.ts` / `tests/schemas.test.ts`. Dialog focus is stabilized so opening does not steal focus from an invalid RUT. ([#96](https://github.com/jonasotoaguilar/serviceflow/pull/96), [#100](https://github.com/jonasotoaguilar/serviceflow/pull/100), [#102](https://github.com/jonasotoaguilar/serviceflow/pull/102))

### Location active invariant and UI projection

At least one active location per tenant is now enforced at every boundary. SQLite triggers `trg_locations_no_last_active_deactivate` / `trg_locations_no_last_active_delete` and `trg_locations_no_history_delete` plus JS guards `onRecordUpdateRequest` / `onRecordDeleteRequest` in `pb_hooks/locations.pb.js` reject deactivating or deleting the last active location and deleting any location with history (`services.locationId || originLocationId` or `service_events.fromLocationId || toLocationId`). `app/actions/locations.ts` `getLocations` computes `hasHistory` and `activeCount` correctly instead of `false`/`0`, paginates with selected fields via `totalItems`/`totalPages` (no arbitrary cap), and guards deletion by current or origin. UI in `components/locations/*` removes the obsolete `Sede Principal` / `isDefault` role: the initial location is bootstrap only; with one active location, deactivate/delete actions are hidden; with ≥2 actives, deactivate appears for actives and delete only where `hasHistory === false`; inactive locations can be reactivated; rename is always allowed. Obsolete skipped default-role tests and casts removed. ([#97](https://github.com/jonasotoaguilar/serviceflow/pull/97), [#99](https://github.com/jonasotoaguilar/serviceflow/pull/99), [#101](https://github.com/jonasotoaguilar/serviceflow/pull/101))

### Registro — plain navigation, origin-immutable metrics, and deterministic backfill

Registro empty-state `Nuevo servicio` now navigates to plain `/dashboard` (no `?createService=1`); the duplicate header pager `page / totalPages` is removed, leaving only the footer pagination. `DashboardPage` no longer reads `searchParams?.createService`. Service identity gains `originLocationId` (immutable origin) across `lib/types.ts`, `lib/schemas.ts`, `lib/storage.ts`, `pocketbase/v1.collections.json` (indexed), `app/api/services/route.ts`, and `pb_hooks/services.pb.js` (enforced on create/update via `$app.findRecordById`). Location metrics in Registro are now authoritative: active counts `pending`/`ready` at current `locationId`, completed counts at `originLocationId`, `cancelled` counts neither — verified in `tests/unit/registro-location-metrics.test.ts`. Direct PocketBase writes that try to bypass origin are rejected by the same triggers/JS guards. Backfill for existing rows is deterministic: JSVM-isolated `backfillOrigin` in `pb_hooks/backfill-origin.pb.js` runs inside `onBootstrap` with `cronAdd`/`cronRemove` retry and also on `onCollectionAfterCreateSuccess` for first-ever import; it resolves origin from the earliest `service_events.kind = 'created'` entry or falls back to `locationId` only when no `location_changed` history exists, leaving truly ambiguous rows unresolved. Pagination for `services` and `service_events` uses selected fields and exact `totalItems`/`totalPages` without the previous 200-record truncation or page-50 cap. ([#103](https://github.com/jonasotoaguilar/serviceflow/pull/103))

### Docker worktree isolation with canonical PocketBase paths

Parallel worktrees no longer collide. `compose.yaml` removes fixed `container_name`, exposes `APP_PORT` (default `3000`) and `POCKETBASE_PORT` (default `8090`) via `.env.example`, and scopes the `pocketbase-data` volume by Compose project name (previously fixed `serviceflow-pocketbase-local-data`). One-time copy for existing data is documented: `docker run --rm -v serviceflow-pocketbase-local-data:/from -v <project>_pocketbase-data:/to alpine cp -a /from/. /to/`. Hooks and migrations mount at the image-canonical paths `./pb_hooks:/pocketbase/hooks:ro` and `./pb_migrations:/pocketbase/migrations:ro` (image `adrianmusante/pocketbase:0.40.1` with healthcheck at `/pocketbase`, non-root 1001). `.dockerignore` excludes worktree runtime dirs `.agents`, `.herdr`, `.codegraph`, `pb_data`, `.sdd` to prevent `ENOENT` during `pnpm build`. Validated via `docker compose config`. ([#104](https://github.com/jonasotoaguilar/serviceflow/pull/104))

## Install

```sh
docker pull ghcr.io/jonasotoaguilar/serviceflow:v2.0.1
docker run --rm -p 3000:3000 ghcr.io/jonasotoaguilar/serviceflow:v2.0.1
```

For local development:

```sh
pnpm install --frozen-lockfile
pnpm run build
pnpm start
```

Environment variables follow `.env.example` (`POCKETBASE_URL`, `APP_PORT`, `POCKETBASE_PORT`, `POCKETBASE_ADMIN_EMAIL`, `POCKETBASE_ADMIN_PASSWORD`); see `docs/tooling/biome.md` and `docs/RELEASING.md` for toolchain and release contract.

## Upgrade

Upgrade is in-place from `v2.0.0`; no data migration is required beyond the automatic `originLocationId` backfill on PocketBase bootstrap.

Record the current image digest before upgrading:

```sh
docker buildx imagetools inspect ghcr.io/jonasotoaguilar/serviceflow:latest --raw | sha256sum > /tmp/pre-v2.0.1-digest.txt
cat /tmp/pre-v2.0.1-digest.txt
```

Then pull and validate:

```sh
docker pull ghcr.io/jonasotoaguilar/serviceflow:v2.0.1
docker pull ghcr.io/jonasotoaguilar/serviceflow:2.0
docker pull ghcr.io/jonasotoaguilar/serviceflow:2
docker pull ghcr.io/jonasotoaguilar/serviceflow:latest
docker buildx imagetools inspect ghcr.io/jonasotoaguilar/serviceflow:v2.0.1 --raw | sha256sum
```

If you previously used the fixed volume `serviceflow-pocketbase-local-data`, copy it once to the new project-scoped volume before first `up` (see What changed). The composed app is at `http://127.0.0.1:${APP_PORT:-3000}` and PocketBase at `http://127.0.0.1:${POCKETBASE_PORT:-8090}` (configurable via `.env`).

- `pnpm exec tsc --noEmit` — type check
- `pnpm run test:run` — Vitest suite (registro-location-metrics, registro-primary-surface, dialog-focus, locations, lifecycle)

- `scripts/release-preflight` with `RELEASE_TAG=v2.0.1` — package version, single release notes, H1, required sections, no placeholder, no `CHANGELOG*`, hooks executable, `Dockerfile` present

The protected release workflow re-runs preflight → release (multi-platform `linux/amd64,linux/arm64` image with OCI labels and four GHCR tags `v2.0.1`, `2.0`, `2`, `latest`) → verify (SHA256 equality over `--raw` manifests and `gh release view` JSON) once `v2.0.1` is pushed.

## Rollback

To revert a deployment upgraded to `v2.0.1` before the next patch:

```sh
PRE_DIGEST="$(cat /tmp/pre-v2.0.1-digest.txt)"
docker pull "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}"
docker tag "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}" ghcr.io/jonasotoaguilar/serviceflow:rollback-pre-v2.0.1
docker run --rm -p 3000:3000 "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}"
```

If no digest was recorded, redeploy the prior `v2.0.0` digest from the registry or rebuild from the commit prior to `v2.0.1`. Do not move the `v2.0.1` tag or delete the published GitHub Release or GHCR image; per the release contract, failures are fixed forward with the next patch (`v2.0.2`).
