# v2.0.0 — Canonical Release Baseline

v2.0.0 establishes the first canonical release baseline for ServiceFlow. It resets the version from 3.2.0 to 2.0.0, replaces the auto-generated changelog with a single curated notes file, and ships the protected release pipeline that all future stable tags will use. Teams deploying ServiceFlow now have a reproducible Docker image, a frozen pnpm baseline, and a fail-closed lifecycle for cutting releases.

## What changed

### Canonical toolchain and quality gate

Biome 2.5.10 replaces ESLint as the single formatter and linter. `biome.json` enforces tab indentation, 100-character line width, and recommended rules, while `pnpm run check`, `pnpm exec tsc --noEmit`, `pnpm run test:run`, and `pnpm run build` run in CI on every push to `main` and on pull requests. Husky and `lint-staged` run `biome check --write --no-errors-on-unmatched` on staged `js/ts/json/css` files. ([#42](https://github.com/jonasotoaguilar/serviceflow/pull/42))

### Protected release lifecycle and hooks

The release workflow (`.github/workflows/release.yml`) implements the three-hook contract `preflight → release (environment: release) → verify` with concurrency grouped per tag, stable-tag trigger `vX.Y.Z` and pre-release exclusion `!v*-*`, exact-tag checkout, least-privilege permissions (`release: contents: write, packages: write`; `verify: contents: read, packages: read`), QEMU and Buildx setup, and ephemeral credential materialization under `$RUNNER_TEMP/release-material` wiped with `if: always()`. Hooks `scripts/release-preflight` (read-only), `scripts/release-publish` (write-capable, builds and pushes `ghcr.io/jonasotoaguilar/serviceflow` with tags `v2.0.0`, `2.0`, `2`, `latest` and creates the GitHub Release via `--notes-file`), and `scripts/release-verify` (read-only, verifies release JSON and four GHCR tags resolve to one digest) are executable and fail closed. ([#43](https://github.com/jonasotoaguilar/serviceflow/pull/43), [#44](https://github.com/jonasotoaguilar/serviceflow/pull/44))

### Secure pnpm baseline

The project standardizes on `pnpm@11.1.1` (`packageManager: pnpm@11.1.1`) with a committed `pnpm-lock.yaml` and hardened `pnpm-workspace.yaml`: `strictDepBuilds: true`, `allowBuilds: [esbuild, sharp]`, `minimumReleaseAge: 20160` (excludes `@types/*`, `typescript`, `@biomejs/*`), `blockExoticSubdeps: true`, `trustPolicy: no-downgrade` (excludes `@types/*`, `trustPolicyIgnoreAfter: 20160`). `pnpm install --frozen-lockfile` is the CI install gate and remains valid.

### Version baseline and curated release notes

Version is reset `3.2.0 → 2.0.0` to mark the first canonical release. The obsolete scripts `changelog` and `version` and the devDependency `standard-version` are removed with no compatibility fallback, and the committed `CHANGELOG.md` is deleted. Curated release notes replace the auto-changelog: this document is the single source of truth at `docs/releases/v2.0.0.md` and is consumed by the release workflow via `--notes-file`.

## Install

Use the published Docker image for this baseline:

```sh
docker pull ghcr.io/jonasotoaguilar/serviceflow:v2.0.0
docker run --rm -p 3000:3000 ghcr.io/jonasotoaguilar/serviceflow:v2.0.0
```

For local development:

```sh
pnpm install --frozen-lockfile
pnpm run build
pnpm start
```

Environment variables follow `.env.example`; see `docs/tooling/biome.md` for toolchain details.

## Upgrade

This is the first canonical release. There is no previous `v2.x` stable tag to upgrade from, so treat `v2.0.0` as the new baseline.

Before upgrading any deployment that was running a pre-canonical build (for example a floating `latest` or commit-pinned image):

```sh
docker buildx imagetools inspect ghcr.io/jonasotoaguilar/serviceflow:latest --raw | sha256sum > /tmp/pre-v2-digest.txt
cat /tmp/pre-v2-digest.txt
```

Record the digest in runbooks or deployment notes. Then pull the baseline image and validate:

```sh
docker pull ghcr.io/jonasotoaguilar/serviceflow:v2.0.0
docker pull ghcr.io/jonasotoaguilar/serviceflow:2.0
docker pull ghcr.io/jonasotoaguilar/serviceflow:2
docker pull ghcr.io/jonasotoaguilar/serviceflow:latest
docker buildx imagetools inspect ghcr.io/jonasotoaguilar/serviceflow:v2.0.0 --raw | sha256sum
```

No database migration or wire-format change is required by this baseline; the change is limited to toolchain, release lifecycle, and version metadata. Rollback must use the digest recorded before the upgrade.

## Verification

Pre-publish verification for this baseline was:

- `pnpm run check` — Biome lint and formatter gate
- `pnpm exec tsc --noEmit` — type check
- `pnpm run test:run` — Vitest suite
- `pnpm run build` — Next.js production build
- `pnpm install --frozen-lockfile` — lockfile validation (passes after removal of `standard-version` and its transitive tree)
- `scripts/release-preflight` — synthetic fixture with `RELEASE_TAG=v2.0.0`, `RELEASE_COMMIT` bound to HEAD, `package.json` version `2.0.0`, single `docs/releases/v2.0.0.md` with correct H1 and required sections, no `CHANGELOG*`, hooks executable, `Dockerfile` present: `preflight ok: v2.0.0`
- Negative preflight cases: missing notes, mismatched H1, placeholder text, extra `docs/releases` file, and `CHANGELOG*` presence correctly fail closed

The protected release workflow will re-run the same preflight, then `release-publish` (multi-platform `linux/amd64,linux/arm64` image with OCI labels `org.opencontainers.image.revision/source/version` and four GHCR tags), and `release-verify` (SHA256 equality over `--raw` manifests for `v2.0.0`, `2.0`, `2`, `latest` plus `gh release view` JSON checks) once a stable tag is pushed.

## Rollback

If a deployment upgraded to `v2.0.0` must be reverted before the next patch baseline:

```sh
PRE_DIGEST="$(cat /tmp/pre-v2-digest.txt)"
docker pull "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}"
docker tag "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}" ghcr.io/jonasotoaguilar/serviceflow:rollback-pre-v2
docker run --rm -p 3000:3000 "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}"
```

If no pre-release digest was recorded, redeploy the previously running `latest` digest from the registry or rebuild from the commit prior to v2.0.0. Do not move the `v2.0.0` tag or delete the published GitHub Release or GHCR image manually; per the release contract, failures are fixed forward with the next patch (`v2.0.1`) and the `release` environment remains protected.
