# v2.0.2 — Release pipeline fix for GHCR multi-platform publish

Patch release that fixes the protected release pipeline so the published GHCR image is actually produced. No application change beyond `v2.0.1`; this tag republishes the `v2.0.1` application payload (service validation, location invariants, Registro origin metrics, and Docker worktree isolation) with working multi-platform GHCR artifacts. Tag `v2.0.1` remains published and immutable; no data migration beyond the `v2.0.1` `originLocationId` backfill is required.

## What changed

### Release workflow — blank `GITHUB_TOKEN` inheritance fix

`release` job used job-level `env: GITHUB_TOKEN: ""` for least privilege but `docker/setup-qemu-action@v4` and `docker/setup-buildx-action@v4` inherited the empty value and failed with `Parameter token or opts.auth is required` (run `33841684717` for `v2.0.1`: `preflight` success, `release` failure at `Set up Docker Buildx`, `verify` skipped, GitHub Release `v2.0.1` created but no GHCR image). Neither action declares a `token` input — `action.yml` has no `token` field and `@docker/actions-toolkit` reads `process.env.GITHUB_TOKEN` — so the empty inheritance broke GH cache/tool-cache authentication.

Fix adds step-scoped `env: GITHUB_TOKEN` (set from `github.token`) to every setup step that requires the token, preserving the blank elsewhere:

- `release` job: `Set up QEMU` and `Set up Docker Buildx` now each carry step-scoped `GITHUB_TOKEN`.
- `verify` job: `Set up Docker Buildx` now carries step-scoped `GITHUB_TOKEN`.

Least privilege is preserved: only the three setup steps and the existing `GH_TOKEN`-scoped publish/verify hooks receive a token; all other steps still see an empty `GITHUB_TOKEN`. No new secret or environment protection is added; `environment: release` remains without approval protection and no external DockerHub secret is required (GHCR only).

Contract test `tests/unit/release-workflow.test.ts` now guards the invariant: job-level blank plus per-setup-step token, and core release-contract markers. Preflight for `v2.0.2` validates single release document, `package.json` version `2.0.2`, H1, and required sections.

References the `v2.0.1` payload in full: service validation and status filter, location active invariant and UI projection, Registro plain navigation with immutable `originLocationId` and deterministic backfill, and Docker worktree isolation with canonical `/pocketbase/hooks` and `/pocketbase/migrations` mounts (see `v2.0.1` notes for full detail). Operators who built `v2.0.1` from source already run this code; `v2.0.2` only ensures GHCR tags resolve correctly.

## Install

```sh
docker pull ghcr.io/jonasotoaguilar/serviceflow:v2.0.2
docker run --rm -p 3000:3000 ghcr.io/jonasotoaguilar/serviceflow:v2.0.2
```

For local development:

```sh
pnpm install --frozen-lockfile
pnpm run build
pnpm start
```

Environment variables follow `.env.example` (`POCKETBASE_URL`, `APP_PORT`, `POCKETBASE_PORT`, `POCKETBASE_ADMIN_EMAIL`, `POCKETBASE_ADMIN_PASSWORD`); see `docs/RELEASING.md` for toolchain and release contract.

## Upgrade

Upgrade is in-place from `v2.0.0` or `v2.0.1`; no data migration is required beyond the automatic `originLocationId` backfill on PocketBase bootstrap introduced in `v2.0.1`. `v2.0.2` application behavior is identical to `v2.0.1`.

Record the current image digest before upgrading:

```sh
docker buildx imagetools inspect ghcr.io/jonasotoaguilar/serviceflow:latest --raw | sha256sum > /tmp/pre-v2.0.2-digest.txt
cat /tmp/pre-v2.0.2-digest.txt
```

Then pull and validate:

```sh
docker pull ghcr.io/jonasotoaguilar/serviceflow:v2.0.2
docker pull ghcr.io/jonasotoaguilar/serviceflow:2.0
docker pull ghcr.io/jonasotoaguilar/serviceflow:2
docker pull ghcr.io/jonasotoaguilar/serviceflow:latest
docker buildx imagetools inspect ghcr.io/jonasotoaguilar/serviceflow:v2.0.2 --raw | sha256sum
```

The composed app is at `http://127.0.0.1:${APP_PORT:-3000}` and PocketBase at `http://127.0.0.1:${POCKETBASE_PORT:-8090}` (configurable via `.env`). Worktree isolation and volume scoping from `v2.0.1` remain unchanged.

## Verification

Pre-publish verification for this release:

- `pnpm run check` — Biome lint gate (formatter disabled)
- `pnpm exec tsc --noEmit` — type check
- `pnpm run test:run` — Vitest suite including `release-workflow` contract, `registro-location-metrics`, locations, and lifecycle
- `docker compose config -q` — compose file, project-scoped volume, canonical mounts, healthcheck, and configurable ports
- `scripts/release-preflight` with `RELEASE_TAG=v2.0.2` — package version, single release notes, H1, required sections, no placeholder, no `CHANGELOG*`, hooks executable, `Dockerfile` present

The protected release workflow re-runs `preflight` → `release` (multi-platform `linux/amd64,linux/arm64` image with OCI labels and four GHCR tags `v2.0.2`, `2.0`, `2`, `latest`) → `verify` (SHA256 equality over `--raw` manifests and `gh release view` JSON) once `v2.0.2` is pushed.

## Rollback

To revert a deployment upgraded to `v2.0.2` before the next patch:

```sh
PRE_DIGEST="$(cat /tmp/pre-v2.0.2-digest.txt)"
docker pull "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}"
docker tag "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}" ghcr.io/jonasotoaguilar/serviceflow:rollback-pre-v2.0.2
docker run --rm -p 3000:3000 "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}"
```

If no digest was recorded, redeploy the prior `v2.0.1` application digest (built from source) or pull the last known good GHCR tag. Do not move the `v2.0.2` or `v2.0.1` tags or delete the published GitHub Releases or GHCR images; per the release contract, failures are fixed forward with the next patch.
