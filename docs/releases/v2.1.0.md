# v2.1.0 — Verified-only accounts and login navigation

Minor release that requires email verification before a usable session exists, and that replaces the hard browser redirect after login/register with Next.js router navigation. Operators who send verification mail must configure Resend SMTP on `pocketbase-init` only. Default tests still pass without SMTP.

## What changed

### Verified-only authentication

Registration creates an unverified PocketBase user, requests verification mail, and does not write `pb_auth`. The user is sent to `/login?registered=1` with an info callout. Login, resend, and unknown addresses stay enumeration-neutral (`Credenciales inválidas` plus a visible resend). PocketBase `users.authRule` is `verified = true`; the app guard also rejects `verified !== true`. The `/verify` callback consumes the token server-side and redirects to `/verify?status=ok|fail` without leaving the token in the URL.

Issue [#108](https://github.com/jonasotoaguilar/serviceflow/issues/108). Stack: [#109](https://github.com/jonasotoaguilar/serviceflow/pull/109)–[#115](https://github.com/jonasotoaguilar/serviceflow/pull/115).

### Login and register navigation

Successful login still uses `router.push("/dashboard")` plus `router.refresh()` instead of `window.location.assign`, which removed the transient "page not found" flash. Register success uses the same router pair targeting `/login?registered=1`.

### Operator mail

`pocketbase-init` applies Resend SMTP when `PB_SMTP_PASSWORD` is set (API key). Host `smtp.resend.com`, username `resend`, port 465, TLS. Sender `ServiceFlow <no-reply@serviceflow.jonasotoaguilar.space>`. Optional `PB_META_APP_URL` overrides the verification origin (default `https://serviceflow.jonasotoaguilar.space`). Unset/empty password skips SMTP; partial config fails closed. Secrets are never mounted on the Next.js app. One operator staging send (`POST /api/settings/test/email` with `{ "template": "verification" }`) is not part of the default suite.

Setting `authRule` rotates the users token secret; existing local sessions must sign in again after upgrade. There is no grandfathering of unverified accounts.

## Install

```sh
docker pull ghcr.io/jonasotoaguilar/serviceflow:v2.1.0
docker run --rm -p 3000:3000 ghcr.io/jonasotoaguilar/serviceflow:v2.1.0
```

For local development:

```sh
pnpm install --frozen-lockfile
pnpm run build
pnpm start
```

Environment variables follow `.env.example` (`POCKETBASE_URL`, `APP_PORT`, `POCKETBASE_PORT`, `POCKETBASE_ADMIN_EMAIL`, `POCKETBASE_ADMIN_PASSWORD`, `PB_SMTP_PASSWORD`, `PB_META_APP_URL`); see `docs/RELEASING.md` for toolchain and release contract.

## Upgrade

Upgrade is in-place from `v2.0.2`. Re-run `pocketbase-init` (or equivalent import) so `users.authRule` is `verified = true` and, if sending mail, SMTP settings are applied. Verify the Resend domain in the Resend dashboard and set `PB_SMTP_PASSWORD` on `pocketbase-init` only. Existing unverified accounts cannot sign in until they confirm email. Local sessions issued before the `authRule` change must log in again.

Record the current image digest before upgrading:

```sh
docker buildx imagetools inspect ghcr.io/jonasotoaguilar/serviceflow:latest --raw | sha256sum > /tmp/pre-v2.1.0-digest.txt
cat /tmp/pre-v2.1.0-digest.txt
```

Then pull and validate:

```sh
docker pull ghcr.io/jonasotoaguilar/serviceflow:v2.1.0
docker pull ghcr.io/jonasotoaguilar/serviceflow:2.1
docker pull ghcr.io/jonasotoaguilar/serviceflow:2
docker pull ghcr.io/jonasotoaguilar/serviceflow:latest
docker buildx imagetools inspect ghcr.io/jonasotoaguilar/serviceflow:v2.1.0 --raw | sha256sum
```

The composed app is at `http://127.0.0.1:${APP_PORT:-3000}` and PocketBase at `http://127.0.0.1:${POCKETBASE_PORT:-8090}`.

## Verification

Pre-publish verification for this release:

- `pnpm run check` — Biome lint gate (formatter disabled)
- `pnpm exec tsc --noEmit` — type check
- `pnpm run test:run` — Vitest suite including auth session, schema artifact, pb-init SMTP skip/apply, and verification UI
- `pnpm test:e2e e2e/smoke.spec.ts` — register without cookie, unverified login denied, verified dashboard; no SMTP
- `scripts/release-preflight` with `RELEASE_TAG=v2.1.0` — package version, single release notes, H1, required sections, no placeholder, no `CHANGELOG*`, hooks executable, `Dockerfile` present

The protected release workflow re-runs `preflight` → `release` (multi-platform `linux/amd64,linux/arm64` image with OCI labels and four GHCR tags `v2.1.0`, `2.1`, `2`, `latest`) → `verify` once `v2.1.0` is pushed.

Known limitations at verification time: Vitest line coverage on `lib/auth.ts` and `app/login/page.tsx` below 80%; Stryker dry-run on `lib/auth.ts` blocked by a source-reading test; operator staging mail send is outside the default suite.

## Rollback

To revert a deployment upgraded to `v2.1.0` before the next patch:

```sh
PRE_DIGEST="$(cat /tmp/pre-v2.1.0-digest.txt)"
docker pull "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}"
docker tag "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}" ghcr.io/jonasotoaguilar/serviceflow:rollback-pre-v2.1.0
docker run --rm -p 3000:3000 "ghcr.io/jonasotoaguilar/serviceflow@${PRE_DIGEST}"
```

If no digest was recorded, redeploy `v2.0.2`. Rolling back the image does not undo a PocketBase `authRule` already applied; restore the previous `users.authRule` if unverified sessions must work again. Do not move the `v2.1.0` or `v2.0.2` tags or delete published GitHub Releases or GHCR images; failures are fixed forward with the next patch.
